# 취약점의 다중 트래픽 증거

취약점 상세 화면의 **연결된 트래픽**에서는 여러 페이지에 걸쳐 기록을 선택하고, 용도와 설명을 입력하고, 순서를 바꾸거나 연결을 해제할 수 있습니다. 트래픽 화면에서도 여러 기록을 선택해 기존 취약점 하나에 한꺼번에 연결할 수 있습니다. 다른 작업에서 상속한 취약점의 증거는 읽기 전용이며, 수정하려면 원본 작업으로 이동해야 합니다.

시스템 설정의 **에이전트 트래픽 자동 연결**은 기본적으로 꺼져 있습니다. `/api/settings`의 `agent_traffic_binding`으로 상태를 읽거나 변경할 수 있으며, 변경 사항은 에이전트의 다음 실행부터 적용됩니다. 이 기능을 켜면 요청과 응답 확인, 도구 호출, 프롬프트 추가로 토큰 사용량이 늘어납니다. 기능을 끄면 자동 연결 인수와 보완 도구를 숨기고 안내문을 주입하지 않으며, 이미 실행 중인 세션이 새 자동 연결을 제출하는 것도 거부합니다. 수동 연결, 트래픽 캡처, 저장된 증거의 조회와 내보내기는 계속 사용할 수 있습니다.

자동 연결을 켠 경우 기본 흐름은 **취약점 등록 → 보고 에이전트 실행 → 트래픽 확인 및 연결 → 최신 증거 버전으로 보고서 작성**입니다. 취약점을 등록하는 에이전트는 `evidence`에 검증 명령, 핵심 출력, 이미 확인한 트래픽 ID와 용도를 남깁니다. 보고 에이전트는 취약점 상세 정보와 실행 기록을 참고해 `traffic_search`와 `traffic_get`으로 실제 기록을 확인한 뒤 `bind_finding_traffic`을 호출합니다. 마지막으로 최신 `version`을 읽고 보고서를 저장합니다. 자동 연결이 꺼져 있으면 보고 에이전트에 원본 트래픽 검색·조회 도구가 추가되지 않지만, 수동으로 연결된 스냅샷은 읽어 보고서에 사용할 수 있습니다.

기존 호출과의 호환성을 위해 `report_finding`의 `traffic_refs`와 `evidence_hint_id`로 제출 시점에 증거를 직접 연결하는 방식도 유지합니다. 연결은 선택 사항입니다. TCP처럼 HTTP가 아닌 취약점이거나, 트래픽이 수집되지 않았거나, 정확한 기록을 찾지 못한 경우에도 취약점을 등록하고 보고서를 작성할 수 있습니다. 이때 검증 명령과 로그 등 확인 가능한 다른 증거를 남기고, 연결하지 않은 이유를 설명하는 것이 좋습니다. 제출한 트래픽 ID는 모두 유효해야 하고 요청·응답 본문을 완전히 읽을 수 있어야 합니다. 하나라도 실패하면 해당 연결 작업이 롤백됩니다. 취약점 등록과 함께 명시적으로 연결한 경우에는 등록 전체가 롤백됩니다. 같은 스냅샷을 다시 추가해도 중복 연결하거나 기존 설명을 덮어쓰지 않습니다.

## 에이전트 도구와 보고서 버전

`report_finding`에 선택적 `traffic_refs` 배열을 전달할 수 있습니다. 배열 순서가 최초 증거 순서가 됩니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "확인한-트래픽-ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "다른-트래픽-ID", "role": "proof", "note": "취약점 재현 요청"}
  ]
}
```

`role`은 `baseline`(정상 대조군), `proof`(취약점 증명), `verification`(추가 검증), `supporting`(보조 증거, 기본값) 중 하나입니다. `traffic_search`와 `traffic_get`으로 실제 기록을 확인하세요. 도메인과 시간은 후보를 찾는 데만 사용하며, 작업 소속을 추정하는 근거로 삼지 않습니다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 안내](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)를 참고하되, 이 프로젝트의 선택적 연결 규칙을 따릅니다. 트래픽 ID를 추측하거나 증거 연결만을 위해 불필요한 재탐색을 하지 마세요.

`report_finding`의 결과 첫 줄은 `finding recorded: <탐색 노드 ID>`입니다. 이어지는 JSON에는 독립 취약점 레코드의 `finding_id`, 탐색 노드의 `finding_node_id`, 연결 결과가 담깁니다.

- `get_finding_traffic(finding_id)`에는 **독립 취약점 레코드 ID**를 사용합니다. 정렬된 증거 목록과 `version`을 반환합니다. `binding_id`, `side=request|response`, `offset`, `length`로 본문을 나누어 읽을 수 있으며, 한 번에 최대 8,192바이트를 반환합니다.
- `update_finding_report`의 `finding_id`는 계속 **탐색 노드 ID**를 사용합니다. `evidence_version`에는 실제로 읽은 버전을 입력하세요. 보고서를 만드는 동안 증거가 바뀌면 이전 버전으로 저장할 수 없으므로 다시 읽고 작성해야 합니다.
- 이전 방식대로 버전 없이 저장한 보고서는 연결된 트래픽 증거까지 반영했다고 표시하지 않습니다. 연결, 설명, 용도 또는 순서가 바뀌면 기존 보고서는 업데이트가 필요하다고 표시합니다.

자동 연결이 켜져 있으면 `add_hint`와 `add_task_hint`에서 개별 힌트나 `hints` 배열의 각 요소에 `traffic_refs`를 저장할 수 있습니다. 플래너가 대신 등록할 때는 `evidence_hint_id`로 이 작업의 힌트를 명시적으로 선택해야 하며, 상속한 힌트는 참조할 수 없습니다. 시스템은 도메인, 시간, 탐색 기록만으로 증거 연결을 추측하지 않습니다. 제출에 실패하면 취약점 일부만 저장되거나 보고 에이전트가 먼저 실행되는 일이 없습니다.

기존 취약점에 빠진 증거는 `bind_finding_traffic(finding_id, traffic_refs)`로 추가할 수 있으며, 취약점을 다시 등록할 필요는 없습니다. `list_findings`, `list_task_findings`, `node_detail`, `get_task_node_detail`은 `finding_id`와 `finding_node_id`를 명시적으로 반환합니다. 기존 `id`는 탐색 노드 ID라는 의미를 유지합니다.

시작 시 기존 도구 스키마에 선택적 속성을 추가하고, 기본 트래픽 도구와 증거 보완 도구를 보고 에이전트에 연결합니다. 사용자가 지정한 도구 연결, 프롬프트, 설명, 활성화 상태는 보존합니다. 안내문은 최종 도구 구성 후 추가됩니다. 취약점을 등록하는 역할은 기존 증거를 전달하고, 보고 에이전트는 기록을 확인해 연결한 뒤 보고서를 작성합니다. 일반 대화에 작업 문맥이 부족하다면 구조화된 힌트로 작업 에이전트에 전달해야 합니다. 확인된 증거가 있다면 작업 완료 전에 전달하되, 증거가 없다는 이유로 완료를 무조건 미루지는 않습니다. 실패한 `report_finding` 호출은 보고 에이전트를 실행하지 않습니다.

## API

기본 경로는 `/api/exploration/findings/{finding_id}/traffic`이며, 여기의 `finding_id`는 독립 취약점 레코드 ID입니다. 기존 인증을 적용하고 `context_task`로 작업의 조회 권한과 상속 데이터의 읽기 전용 여부를 검사합니다.

| 메서드 / 상대 경로 | 요청 및 응답 |
| --- | --- |
| `GET` | 정렬된 증거 요약, 증거 버전, 보고서가 사용한 버전 |
| `POST` | `{"traffic_refs":[...]}` 배열 전체 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`. 전체 목록을 보내야 합니다. |
| `GET /{binding_id}` | 스냅샷 메타데이터와 제한된 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`로 본문 조회. `download=1`은 원본 바이트 전체를 내려받습니다. |

버전 또는 순서 충돌과 보관 중 쓰기는 `409`, 상속 데이터 수정은 `403`, 존재하지 않거나 해당 취약점에 속하지 않는 연결은 `404`를 반환합니다. 트래픽이나 첨부 파일을 읽거나 검증하지 못해도 명시적인 오류를 반환합니다.

## 저장과 마이그레이션

시작 시 PostgreSQL 스키마를 반복 실행해도 안전하게 이전합니다. `traffic_evidence_snapshots`, `finding_traffic_bindings`, `findings.evidence_version`, `findings.report_evidence_version`를 추가하며, 두 버전의 기본값은 0입니다. 과거의 텍스트를 근거로 증거 연결을 추측하지 않습니다.

스냅샷에는 원본 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청·응답 헤더, 본문 길이, SHA-256 해시를 저장합니다. 본문은 해시에 따라 `<data>/evidence/blobs/<앞 두 자리>/<hash>.bin`에 저장합니다. 정리 대상인 `data/traffic`과 분리되어 있고 여러 취약점이 스냅샷과 본문을 공유할 수 있습니다. 스냅샷 수정 API는 없으며, 무결성 검증에 실패하면 조회와 내보내기가 실패합니다.

원본 트래픽의 쓰기 잠금을 잡은 상태에서 큰 blob과 이전 저장 형식까지 포함해 본문 전체를 읽습니다. 파일을 먼저 영구 저장하고 검증한 뒤, PostgreSQL 트랜잭션 하나로 탐색 노드, 의도 관계, 취약점, 스냅샷, 연결을 기록합니다. 커밋 후에만 플래너에 알립니다. 실패 시 참조되지 않는 파일은 남을 수 있지만 업무 레코드가 일부만 만들어지지는 않습니다.

PostgreSQL advisory lock `7337741004`로 증거 파일과 SQL 참조를 조정합니다. 작업 행 잠금은 보관이 대기열에 들어간 뒤 증거가 바뀌지 않게 합니다. 복원 중에는 본문 파일 설치부터 메타데이터 커밋까지 증거 잠금을 유지합니다. 취약점을 삭제하면 연결도 연쇄 삭제됩니다.

정리 작업은 한 시간마다 실행되며, 참조가 없고 진행 중인 작업에서도 쓰지 않는 본문만 최소 24시간 뒤에 제거합니다. 일반 트래픽 정리는 증거 디렉터리에 영향을 주지 않습니다. 실행 중인 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 함께 백업하세요.

## 내보내기와 보관

Markdown에는 순서가 있는 증거 목록과 버전이, JSON에는 메타데이터가, CSV에는 증거 수와 연결 ID가 포함됩니다. `md-zip`은 취약점 Markdown과 다음 파일을 함께 담습니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 요청·응답 파일을 참조합니다. 다운로드 전에 첨부 파일 복사, 해시 검사, 압축, 디스크 동기화와 ZIP의 모든 항목에 대한 CRC 읽기 검사를 끝냅니다. 파일이 없거나 손상되면 다운로드 전체가 실패합니다. 첨부 파일의 원본 바이트는 그대로 보존합니다.

보관 형식 v3은 원본 트래픽이나 도메인에 의존하지 않고 취약점 연결을 따라 스냅샷과 본문을 수집합니다. 패키지 검증이 끝난 뒤에만 실행 중인 데이터를 정리하며, 다른 곳에서도 참조하는 증거는 유지합니다. 복원할 때는 본문을 설치하고 검증한 뒤 트랜잭션으로 메타데이터와 연결을 복원합니다. 실패 시 재시도할 수 있고 v1/v2 보관 파일도 계속 복원할 수 있습니다. 오래된 보관 파일에 없는 새 버전 필드는 0으로 채웁니다.

## 검증과 제약

테스트 패키지마다 별도의 새 PostgreSQL 데이터베이스를 만들고 `ARTEX_PG_DSN`으로 지정하세요. 이전 작업이나 모델 데이터 때문에 백그라운드 실행이 시작되는 일을 막을 수 있습니다. 관련 패키지의 테스트를 실행하고 설정 부족으로 건너뛴 테스트가 없는지 확인합니다.

```sh
# 각 패키지를 실행하기 전에 ARTEX_PG_DSN을 독립 테스트 DB로 지정합니다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드는 `npx tsc --noEmit`, 변경 파일의 Biome 검사, Webpack 빌드, `NEXT_EXPORT=1` 정적 내보내기로 확인합니다. 실행 중인 개발 서버의 캐시를 덮어쓰지 않도록 별도 캐시 디렉터리를 사용하세요.

로컬 종단 간 검증은 별도 포트와 임시 데이터 디렉터리에서, 통제할 수 있는 HTTP 및 도메인 HTTPS 대상을 사용해 진행합니다. 두 연결 경로, 페이지 간 선택, 순서와 설명 변경, 오류 메시지, 상속 데이터의 읽기 전용 동작, 원본 트래픽 삭제 후 다운로드와 내보내기, 보관·정리·복원·해시 검증을 확인합니다.

첫 버전은 증거 조정 잠금 하나를 공유하므로 대량 연결·내보내기나 느린 첨부 파일 다운로드 중에는 다른 증거 작업이 기다릴 수 있습니다. 캡처 기록이나 전체 본문이 없으면 증거를 만들어 낼 수 없습니다. 이 기능은 트래픽 캡처 스위치를 바꾸지 않으며, IP 주소로 HTTPS에 직접 접속할 때 발생하는 인증서 문제도 다루지 않습니다.
